# G9N9N 真机验证与调试历史

本页按硬件/固件批次汇总已知 G9N9N 的**三类真机 HID 表现**及实测记录：

1. **Fully Supported 设备（`HID 版本 0x0110`，完整 3 字节 report 1）**：单键按下与松开均发出完整 3 字节索引格式报告，macOS 正常认识并送达公开 `IOHID` → 进入 **Fully Supported（完全支持）** 模式，语音键与全部 14 颗普通按键完整可用。
2. **Partially Supported 设备（`DIS A0 / 固件 26.7`，1 字节短 report 1）**：描述符声明 2 槽位，但单键与松开仅发出 1 字节，被 macOS 在进入公开 `IOHID` 前丢弃；只有同时按两个键凑齐长度才进入公开 `IOHID` → 进入 **Partially Supported（部分支持）** 模式，仅保留语音键与「方向键 + OK」发送 Enter。
3. **`HID 版本 0x011B` 批次（社区反馈，详见 [brightac/remote-buddy#7](https://github.com/brightac/remote-buddy/issues/7)）**：使用 Report ID `2`（小端 16-bit consumer usage，涵盖 14 键编码），描述符声明不含 ID 3 字节、但固件实际仅发送 2 字节（如按下 `42 00`、松开 `00 00`），导致报告在 macOS `BTLEServer` 层即被长度校验丢弃——**公开 `IOHID` 既收不到单键，也收不到双键**；ATVV 语音链路走 GATT 不受 HID 影响仍可使用。Remote Buddy 连接页会读取并显示 PnP / IOHID 中的 **HID 版本**（如 `0x0110` / `0x011B`）供用户快速鉴别批次，但依据只使用公开系统接口的原则，不通过读取系统调试日志绕过 `BTLEServer`。

版本识别、模式说明与操作指南见 [G9N9N 语音与按键使用指南](g9n9n-compatibility.md)。

## 二、部分支持版本测试记录（2026-10-28，`A0 / 固件 26.7`，单键不可用）

本轮样机的系统身份为 Google Inc.、VID/PID `18D1:9450`、DIS 型号 `A0`、固件 `26.7`；主机为 macOS 15.8.1（24H32），测试时 App 为 26.10.26 / 497。

### 故障现象与根因定位

**设备声明 report 1 包含两个 8 位按键槽位（GATT value 应为 2 字节、加上 report ID 后为 3 字节），但实测单独按键及松开通知只发出 1 字节，未补齐第二槽位；macOS 蓝牙 HID 在进入公开 `IOHID` 之前即丢弃所有 1 字节短报告，因此应用完全收不到任何单键按下或松开事件。**

使用 Apple PacketLogger（HCI/ACL 抓包）与独立 IOHID 观测器同时对照（2026-10-28 新加坡时间，handle `0x0046`、ATT CID `0x0004`、opcode `0x1B`、attribute handle `0x0046`）：

| 操作阶段 | 时间 | GATT value（不含 report ID） | value 长度 | 同时运行的 IOHID 回调 |
| --- | --- | --- | --- | --- |
| 上键按下，第 1 次 | 14:27:23.410 | `03` | 1 | **无（被 macOS 丢弃）** |
| 上键松开，第 1 次 | 14:27:23.678 | `00` | 1 | **无（被 macOS 丢弃）** |
| 上键按下，第 2 次 | 14:27:25.017 | `03` | 1 | **无（被 macOS 丢弃）** |
| 上键松开，第 2 次 | 14:27:25.266 | `00` | 1 | **无（被 macOS 丢弃）** |
| 上键按下，第 3 次 | 14:27:27.042 | `03` | 1 | **无（被 macOS 丢弃）** |
| 上键松开，第 3 次 | 14:27:27.324 | `00` | 1 | **无（被 macOS 丢弃）** |
| 单独按住返回 | 14:30:09.232 | `0B` | 1 | **无（被 macOS 丢弃）** |
| 加按上键，形成双键 | 14:30:09.322 | `03 0B` | 2 | **`01 03 0B`，report ID 1，3 字节** |
| 分步只松开上键（仍按返回） | 14:30:12.190 | `00` | 1 | **无（被 macOS 丢弃）** |
| 全部松开 | 14:30:15.081 | `00` | 1 | **无（被 macOS 丢弃）** |

- 合规的单按上键 value 应为 `03 00`、全松开应为 `00 00`，但该固件只发送 `03` 和 `00`（L2CAP 实测仅 1 字节）。
- **语音键不受影响**：Google Assistant 语音键与麦克风走独立蓝牙 ATVV 协议，按住说话与松开停止均可稳定工作。
- **双键组合可到达 `IOHID`**：同时按下两个键（例如 `OK + 方向键`）恰好填满 2 字节，macOS 会完整递交给公开 `IOHID`；但因松开通知仍是 1 字节 `00` 且被系统丢弃，应用收不到松开边沿，因此不能进入长按／连发／单键映射管线，只适合在“部分支持兼容模式”下提供「方向键 + OK」单次发送 Enter 键。

## 三、ATVV 免提开麦（`0x0C / MIC_OPEN`）与“按一下开始 / 再按停止”可行性验证（2026-11-17，`FW 26.2`）

2026-11-17，在完全支持批次真机（`Chromecast Remote`、VID/PID `18D1:9450`、DIS `A0`、`kBTFirmwareRevisionKey = 26.2`、`kBTHardwareRevisionKey = PVT/MP`、`Report ID 1` 3 字节索引格式）上完成 ATVV 控制帧实测，核查 G9N9N 能否支持“按一下开始、再按一下停止”的免提切换收音。

### 1. 物理语音键默认固件行为（HTT 按住说话）

- **能力协商（`GET_CAPS -> 0x0B`）**：宿主发送 `0a 01 00 00 03 03` 后，硬件返回 `0b 01 00 02 03 00 a0 00 00`（ATVV v1.0、16 kHz IMA-ADPCM `0x02`、帧长 `160`、能力字节 `0x03`）。
- **按下物理语音键**：硬件不等宿主下发 `MIC_OPEN`，主动上送 `04 03 02 <session>`（第 2 字节 `0x03` 对应 ATVV Hold-to-Talk 按住模式）并附带 `0x08`（`START_SEARCH`）。
- **松开物理语音键**：固件立刻主动发送 `0x00`（`AUDIO_STOP`，日志记录为 `reason=remote_notification close_requested=false`）并停流。与 `T1-Remote`（首次松手不发 `0x00`）不同，G9N9N 物理语音键自身会在松手时停止硬件推流。

### 2. 宿主主动发 `MIC_OPEN`（`0x0C`）免提开麦实测结果

在**不按遥控器任何按键**的前提下，直接通过 CoreBluetooth 向 ATVV TX（`AB5E0002-...`）下发命令，实测证明 G9N9N 固件支持电脑主动开麦、持续推流并由电脑关麦：

| 时间点 | 方向与命令 | 实测回包 / 现象 |
| --- | --- | --- |
| `0.413s` | Host 写 `MIC_OPEN`（`0c 00`） | 无按键状态下请求 16 kHz 开麦 |
| `0.439s`（+26 ms） | Remote 通知 CTL | 返回 `AUDIO_START`：`04 00 02 00`（触发位 `0x00`、16 kHz `0x02`、session `0x00`） |
| `0.606s`–`0.609s`（约 +195 ms） | Remote 通知 CTL + AUDIO | 收到 Sync 帧 `0a 02 00 00 00 00 00`，随后以每帧 `160` 字节持续收到 16 kHz IMA-ADPCM 音频流 |
| `1.913s` | Host 写 `MIC_EXTEND`（`0e 00`） | 已收 `66` 包 / `10,560` 字节；发送保活后流持续正常 |
| `3.106s` | Host 写 `MIC_CLOSE`（`0d 00`） | 总计收到 `126` 包 / `20,160` 字节（约 2.7 秒免提音频） |
| `3.127s`（+21 ms） | Remote 通知 CTL | 返回 `AUDIO_STOP`：`00 00`，音频流干净停止 |

### 3. 两种可行实现路线与待验证边界（当前暂未实现）

1. **普通按键映射「切换持续录音（`toggleLongRecording`）」**：在完全支持单键报告的 G9N9N 上，可由普通按键（如 `输入源`、`Netflix` 等）直接触发 `0x0C` 开麦、再按一次发 `0x0D` 关麦，不存在硬件断流重启空窗。
2. **语音键短按自动重开（类 `rc003VoiceExtension`）**：若要复用物理语音键，需要在短按松手触发 `0x00` 后立即回发 `0x0C 00` 重开免提流（长按超过阈值仍松手即停）；每次短按重启麦克风存在约 **`~195 ms`** 的硬件启动空窗（`0.413s -> 0.609s`）。

若后续决定启用上述任一模式，还需先补两项实机边界确认：
1. **单次免提超时与保活上限**：纯 `0x0C` 打开后不触碰按键时，固件是否会主动超时断流（以及周期发送 `0x0E MIC_EXTEND` 能否持续延长时间）。
2. **`0x0C` 流进行中再次按下物理语音键的帧格式**：确认二次按下时 CTL 上报的是 `0x08` 还是带新 session ID 的 `0x04 03 02 xx`，以便软件统一识别为“第二次按 → 下发 `0x0D` 停止”。
